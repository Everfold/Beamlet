# 数据库无关的持久化方案

状态: 设计方案, 尚未实现存储接口或恢复入口. 原语与流程以 [内核规范](kernel.md) 为准.

## 1. 目标与范围

持久化保存三种原语的不可变数据, Operation 的已提交变更, 以及当前状态快照. 日志与快照是存储记录, 不增加领域原语. Attempt 和 Report 没有各自的生命周期状态机.

方案约束逻辑记录, 读写结果与失败语义. 不规定物理表数量, 数据库产品, 查询语言, 驱动, 序列化库或消息中间件.

本方案主要覆盖 Authority 的权威生命周期存储. Worker 可以使用其中的 Report 保存能力. Worker 的业务执行检查点和报告交付进度不属于 Operation 生命周期快照.

## 2. 三类持久化记录

| 类别 | 保存内容 | 可变性 |
| --- | --- | --- |
| 原语数据 | Operation 的身份与原始请求, Attempt, Report | 创建后不可覆盖 |
| Operation 变更记录 | 按 revision 排序的已提交生命周期事实 | 仅追加 |
| Operation 当前快照 | 当前状态及已应用 revision | 由提交动作派生并更新 |

逻辑上分为这三类, 实现可以使用三组记录或分别保存三种原语. 不要求每类对应一张物理表.

### 2.1 原语数据

| 原语数据 | 字段 | 唯一性与引用 |
| --- | --- | --- |
| Operation | operation_id, 原始请求 | operation_id 唯一 |
| Attempt | attempt_id, operation_id | attempt_id 唯一, 引用所属 Operation |
| Report | report_id, operation_id, attempt_id, 结果 | report_id 唯一, 保存两个引用身份 |

这里保存的 Operation 数据是其不可变部分, 生命周期单独投影为变更与快照. 身份不限定为 UUID; 三种原语的身份使用各自的命名空间, 不要求不同种类之间的身份值互不相同.

同一身份与完全相同的数据重复保存视为已有数据. 同一身份对应不同数据时返回身份冲突, 不采用最后写入覆盖. Attempt 身份不能通过更换 Operation 来复用.

数据保存的幂等性不代表可以再次创建授权. 创建 Attempt 的新提交必须使用从未用于已提交创建的 Attempt 身份, 即使旧数据完全相同也不能复用. 确认同一次创建成功只能重试原 commit_id, 不能在 Ready 后用新提交重新创建旧 Attempt.

Report 可以先作为证据保存, 再由 Authority 决定接受. 单独保存 Report 不校验本地是否已有其引用对象, 不推进 Operation, 也不表示该报告已经被接受. 接受时必须确认引用对象存在且关联匹配. 这样 Worker 的本地存储不需要持有 Operation 生命周期.

### 2.2 Operation 变更记录

每个 Operation 拥有独立的连续 revision, 从 0 开始. 没有跨 Operation 的全局顺序要求.

每条记录包含以下信息:

| 字段 | 含义 |
| --- | --- |
| operation_id | 所属 Operation |
| revision | 此 Operation 的已提交变更序号 |
| commit_id | 本次提交的幂等标识, 在此 Operation 内唯一 |
| change | 下表的一种已发生变化及其引用身份 |
| format_version | 记录格式版本 |

| 变化 | 引用的不可变数据 | 状态规则 |
| --- | --- | --- |
| Operation 已创建 | Operation 数据 | 不存在 -> Ready, revision 为 0 |
| Attempt 已创建 | Attempt | Ready -> AwaitingReport(attempt_id) |
| Report 已接受 | Report | 对应等待状态 -> Ready |
| Operation 已关闭 | 当前 Operation | Ready -> Closed |

变化种类决定所需字段, 不使用一组可任意组合的可空字段. 时间戳可以作为诊断元数据, 不参与排序或合法性判断.

只记录已提交的合法事实. 非法报告与拒绝原因可以单独审计, 不进入成功转换序列. 重复关闭不追加变更, 不递增 revision.

commit_id 是存储请求的幂等标识, 不是新的领域原语或执行授权. 它由调用者提供, 重试同一次提交时保持不变.

### 2.3 Operation 当前快照

快照包含 operation_id, applied_revision, format_version, 以及以下状态之一:

| 状态 | 附加数据 |
| --- | --- |
| Ready | 无 |
| AwaitingReport | 当前等待的 attempt_id |
| Closed | 无 |

只有等待状态携带 Attempt 身份. 快照不保存 Rust 类型名, 库生成的私有状态机或业务执行进度. 原始请求通过 operation_id 关联, 不在每份快照中重复编码.

首版每次成功提交都同步更新当前快照. 因而正常加载时 applied_revision 等于已提交日志末尾的 revision. 不引入异步快照更新或日志裁剪.

日志是生命周期事实的恢复依据, 快照是可重建投影. 缺少快照不能被解释成 Operation 从未存在; 是否存在以已提交的创建事实为准.

## 3. 编码与版本

身份编码必须稳定且可比较, 保留调用者定义的身份语义. 请求与结果作为带编码标识和业务格式版本的不透明内容保存, 适配器不解释业务内容.

原语和日志的结构版本与业务请求/结果版本分开管理. 不固定 JSON, 二进制格式或 Rust serde. 选择某种编码不应改变上述提交和恢复语义.

构造提交请求时冻结其身份, 预期版本, 变化种类与原语内容编码. 重试复用完全相同的请求, 不重新生成身份或加入随重试变化的时间字段. 幂等比较可以针对这份固定编码, 不要求任意业务类型实现 Eq 或 Clone.

未知版本或无法解码的数据必须报告错误, 不能跳过记录, 生成默认身份或将 Operation 重置为 Ready. 后续需要显式迁移格式时, 保留身份与历史事实的含义.

## 4. 单 Operation 的提交契约

### 4.1 提交输入

每次提交只推进一个 Operation. 公共提交头包含 operation_id, commit_id, expected_revision 与记录格式版本.

expected_revision 有两个互斥形式:

- NotCreated: 仅用于创建尚不存在的 Operation.
- Exact(n): 仅当该 Operation 的已提交末尾版本等于 n 时允许推进.

提交内容为以下四种之一:

| 提交内容 | 携带数据 | 成功后必须持久化的效果 |
| --- | --- | --- |
| 创建 Operation | 不可变身份与请求 | Operation 数据, revision 0 的创建记录, Ready 快照 |
| 创建 Attempt | 完整 Attempt | Attempt 数据, 下一条创建记录, 等待快照 |
| 接受 Report | 完整 Report | Report 数据或确认已有相同数据, 下一条接受记录, Ready 快照 |
| 关闭 Operation | 无新增原语 | 下一条关闭记录, Closed 快照 |

调用者不能任意指定提交后的快照或 revision. 它们由当前已提交状态与合法变化计算得到.

### 4.2 校验与原子可见性

逻辑执行顺序如下. 具体实现可以合并步骤, 但对外行为必须一致.

1. 查找此 Operation 内的 commit_id. 已提交且请求相同则返回原提交凭据; 同一标识绑定不同请求则返回提交标识冲突.
2. 比较 expected_revision 与权威日志末尾. 不匹配则拒绝本次提交, 不写入任何本次数据.
3. 校验当前状态, 原语身份唯一性及引用. 创建 Attempt 必须使用新身份且匹配 Operation; 接受 Report 要匹配当前 Operation 与等待中的 Attempt, 可以使用已预存的相同报告.
4. 生成下一 revision 与状态快照, 将新增原语, 变更记录和快照作为一个原子提交持久化.
5. 返回可用于确认本次提交的 operation_id, commit_id 与 applied_revision.

首步必须先于当前状态校验. 否则一个已成功接受报告但响应丢失的提交, 重试时会被 Ready 状态错误地拒绝.

同一 Operation 的提交判定必须可线性化, 幂等检查与版本比较不能留下竞争窗口. 并发的相同请求应分别得到 Applied 和 AlreadyApplied; 发现版本变化时, 在返回冲突前确认是否正是同一提交已经成功. 同一原语身份的并发创建也必须保持唯一性, 不能让不同 Operation 都成功占用同一 Attempt 身份.

对外不能观察到只有 Attempt 而没有对应等待事实, 或只有接受事实而没有完整 Report 的中间状态. 不要求跨 Operation 原子提交, 也不要求跨 Authority 与 Worker 存储的分布式事务.

原子提交是适配器必须兑现的语义, 不要求后端暴露事务对象. 实现可以使用事务, 条件原子替换, 或带提交标记的日志等机制. 三次独立写入且没有一致可见性与崩溃恢复措施, 不满足本契约.

### 4.3 返回结果与失败

成功结果区分以下三种:

| 结果 | 含义 |
| --- | --- |
| Applied | 本次新增了一条已持久化变更 |
| AlreadyApplied | 同一 commit_id 和请求已提交, 返回原 applied_revision |
| NoChange | 当前已经 Closed 且预期版本匹配, 重复关闭不产生变更 |

重复关闭的 NoChange 不创建幂等凭据或变更记录. Closed 没有后续生命周期变化, 相同的关闭请求再次执行仍是 NoChange. 已有 commit_id 的匹配和冲突判断优先于这个分支.

错误至少区分以下类别:

| 类别 | 含义与调用方动作 |
| --- | --- |
| 版本冲突 | 当前 head 与预期不同; 加载新状态后重新决定动作 |
| 身份冲突 | 某原语身份已绑定不同数据; 修正身份或数据 |
| 提交标识冲突 | commit_id 被用于不同请求; 不得当作成功重试 |
| 非法变化或数据 | 非法状态, 引用不匹配, 数据缺失或格式不支持; 拒绝推进并报告原因 |
| 存储失败 | 明确标注 DefinitelyNotApplied 或 OutcomeUnknown |

OutcomeUnknown 表示响应无法确认是否持久化, 不是失败回滚的承诺. DefinitelyNotApplied 则必须确认该提交确实未生效; 仅知道本次调用尚未写入, 不能排除上一次尝试已经成功.

调用者复用原提交请求及 commit_id 重试, 直到确认 Applied/AlreadyApplied 或获得可确定的冲突结果. 不能为同一次重试生成新 Attempt 或新 commit_id.

同一原语身份且内容相同, 不自动代表某次状态转换已经提交. 只有相同提交凭据确认后才返回 AlreadyApplied. 用新的 commit_id 再次接受旧报告, 仍须按当前状态校验.

AlreadyApplied 的 applied_revision 可能早于现在的 head. 它证明旧提交成功, 不证明 Operation 仍处于当时状态. 收到该结果后重新加载当前视图, 再决定后续动作.

## 5. 数据库无关的能力接口

以下是逻辑方法, 不是已实现的 Rust trait. 方法名不规定同步或异步, 不包含 SQL, 连接, 事务句柄或驱动类型. 实现阶段可以组合为小接口, 不要求每张物理表对应一个接口.

变化校验与重放由可复用的纯逻辑模块提供, 按内核规则推进并派生快照. 适配器在自己的原子提交判定中使用这份逻辑, 无需各自维护另一套生命周期规则. 适配器负责持久化, 一致可见性和耐久性, 业务结果不参与状态转换判断.

### 5.1 共享原语数据能力

| 方法 | 输入 | 结果与约束 |
| --- | --- | --- |
| 保存 Report | 完整编码 Report | 新增或已存在相同数据; 不改变 Operation 状态 |
| 读取原语数据 | 原语种类与身份 | 返回不可变数据或不存在 |

只有创建 Operation/Attempt 的提交能新增对应权威原语. 不开放任意覆盖原语的操作. Worker 可使用 Report 保存能力, 无需依赖 Operation 的类型状态实现.

### 5.2 Authority 生命周期能力

| 方法 | 输入 | 结果与约束 |
| --- | --- | --- |
| 提交变化 | 第 4 节的完整提交请求 | 原子推进, 幂等结果或明确错误 |
| 加载 Operation | operation_id | 一个一致的已提交视图 |
| 读取变更 | operation_id, 起始 revision, 固定终止 head, 分页参数 | 连续的已提交记录, 可同时附带所引用的原语数据 |
| 扫描 Operation | 不透明游标与条数上限 | 已存在 Operation 身份的可续读分页 |

加载视图至少包含不可变 Operation 数据, 当前快照, 已提交 head 及 head 对应的变更. 等待时还需关联的 Attempt; head 为报告接受记录时还需对应 Report, 使恢复后的 Authority 能继续决定下一步.

分页读取变更固定终止 head, 避免恢复过程追逐不断增加的记录. 读取原语与记录都只能看见已提交数据, 不依赖后端的隔离级别名称.

扫描不得因状态更新而遗漏扫描开始前已存在且未删除的 Operation. 允许重复返回身份, 调用者按身份去重; 扫描期间新建的 Operation 可以由下一轮发现. 第一版不依赖会随状态移动的过滤结果来完成全量发现.

不提供单独追加生命周期日志或随意设置当前快照的方法, 防止调用者绕过原子提交. 快照重建属于受控修复操作, 不是普通业务写接口.

## 6. 类型状态与持久化的衔接

当前 kernel 的 Operation 消费自身并返回新类型, 而持久化格式必须使用可读取的状态标记. 这两种表示不能直接等同.

计划为 kernel 补充只读状态导出与显式恢复入口. 恢复加载方按状态标记分派到对应的类型状态, 不恢复库的内存结构.

| 持久化状态 | 恢复所需校验 | 目标 |
| --- | --- | --- |
| Ready | Operation 数据存在, 对应的已提交状态确为 Ready | Operation<O, P, Ready> |
| AwaitingReport(a) | 上述一致性成立, Attempt a 存在且所属 Operation 匹配 | Operation<O, P, AwaitingReport<A>> |
| Closed | 已提交状态为 Closed | Operation<O, P, Closed> |

恢复时校验已接受 Report 的两个引用与其当时等待的 Attempt 一致. 格式转换与恢复构造不会创建新的授权, 报告或历史记录.

正常执行时, kernel 首先计算候选新对象, Authority 将对应数据与变化提交给存储. 提交确认前, 候选对象不代表权威状态, 不能交付新的 Attempt 或继续提交依赖它的动作.

版本冲突或明确未提交时, 不把候选新对象当作成功结果. 必要时从权威视图恢复原状态类型. OutcomeUnknown 时先确认同一提交, 不通过反向状态转换猜测回滚.

如果新创建 Operation 的首次提交未成功, 调用者可以保留尚未生效的候选请求重试; 不能将它宣告为已持久化 Operation.

## 7. 提交, 交付与恢复流程

### 7.1 正常流程

1. 创建并提交 Operation, 得到 Ready 的权威状态.
2. kernel 创建候选 Attempt 与等待状态; 原子提交后才将请求所需数据与 Attempt 交给 Worker.
3. Worker 执行结束, 生成并按需保存 Report; 交回 Authority.
4. Authority 校验并提交 Report 接受事实, 同步保存完整报告与 Ready 快照.
5. Authority 根据结果提交新的 Attempt 或关闭; Closed 重复关闭不新增事实.

Worker 的本地 Report 保存和 Authority 的接受提交可以位于不同存储. Authority 接受时持久化自己需要的完整报告, 不依赖一个可能消失的远端临时引用.

### 7.2 重建 Operation

1. 加载一致视图并固定已提交终止 head. 不存在创建事实时才返回 Operation 不存在.
2. 校验快照版本, 数据关联及 applied_revision. 首版正常快照应已到达 head.
3. 如使用较旧的可验证快照, 从其后一条记录重放到固定 head. 缺少快照时可由创建事实开始重建.
4. 校验连续版本, 合法转换与引用数据, 构造对应类型状态的 Operation.
5. 重建完成后, Authority 再决定尚未提交的下一步动作.

重放阶段只应用已提交事实, 不再次执行 Worker, 重新生成身份, 接受新报告或执行历史策略. 快照与日志矛盾, 存在缺口或引用数据缺失时报告损坏, 不重置为 Ready 或静默跳过.

正常加载信任通过适配器原子提交维护的快照前缀, 做格式, head 关联与所需引用检查, 不要求每次扫描全部历史. 全量重放用于验证, 迁移或修复; 重放时检查每一条历史转换, 包括 Closed 不得重新打开.

修复快照时, 只有确认日志与原语数据完整有效后才重建. 写回前检查 head 未改变, 防止较旧重建结果覆盖新状态. 无法确认一致性时停止该 Operation 的推进, 保留数据供排查.

### 7.3 恢复之后能做什么

| 状态 | 后续动作 |
| --- | --- |
| Ready 且 head 为创建记录 | 可以制定首次执行决定 |
| Ready 且 head 为报告接受记录 | 根据已保存结果制定尚未提交的重试或关闭决定 |
| AwaitingReport | 等待/查找报告, 或按外层交付协议继续交付同一个 Attempt |
| Closed | 保持关闭 |

等待状态不证明 Worker 未开始执行或已停止执行. 重交付同一 Attempt 不增加授权, 但存储提交本身不保证 Worker 只执行一次. 业务执行恢复需要独立的幂等性或检查点机制.

## 8. 适配器验收场景

所有适配器用同一组存储契约验收, 不是只检查 CRUD 返回值.

### 提交与身份

| 场景 | 必须得到的结果 |
| --- | --- |
| 不同 commit_id 的并发推进使用相同预期 revision | 最多一个推进 head, 另一个得到版本冲突 |
| 相同 commit_id 与相同请求重试 | 原提交凭据, 不重复追加记录 |
| 相同 commit_id 用于不同请求 | 提交标识冲突, 不写入新数据 |
| 同一原语身份携带不同数据 | 身份冲突, 不覆盖旧数据 |
| Ready 下用新提交复用旧 Attempt 身份 | 拒绝再次授权, head 不变 |
| Closed 重复关闭 | NoChange, revision 不变 |

### 报告与崩溃

| 场景 | 必须得到的结果 |
| --- | --- |
| 单独保存 Report | 原 Operation 状态不变 |
| 接受关联错误或旧 Attempt 的 Report | 拒绝, 原 head 和快照不变 |
| 提交任意内部写入点崩溃 | 恢复后只看到完整提交或完全未提交 |
| 提交成功后响应丢失 | 原请求重试可确认成功, 不重复授权或追加 |
| Attempt 提交后交付中断 | 恢复后仍关联同一个 Attempt, 不生成新身份 |

### 读取与恢复

| 场景 | 必须得到的结果 |
| --- | --- |
| 三种状态分别恢复 | 身份与请求不变, 待处理 Attempt 正确 |
| 缺少快照但日志完整 | 从创建事实重建, 不误认为不存在 |
| 日志缺口, 引用缺失或未知版本 | 明确错误, 不跳过或重置 |
| head 在幂等重试后已经前进 | 返回原凭据, 重新加载后不退回旧状态 |
| 扫描期间状态变化 | 不遗漏开始前已有 Operation |

仅内存实现可以验证逻辑语义, 不能据此宣称崩溃持久化成立. 每个真实适配器还需在其承诺的进程/存储故障范围内执行故障注入, 并定义成功响应对应的耐久性保证.

## 9. 实现顺序

1. 在数据库无关的模块中定义记录与提交结果, 为 kernel 添加状态导出及校验恢复入口.
2. 实现确定性的重放与引用校验, 用内存适配器验证状态和提交契约.
3. 将共享 Attempt/Report 数据能力与 Authority 生命周期能力按依赖需要拆开, Worker 不依赖类型状态实现.
4. 选择实际存储后实现适配器, 执行相同契约与故障注入验收.

首版不做日志裁剪, 跨 Operation 事务, 任意历史改写或自动业务重执行. 需要扩展时单独定义其语义, 不改变本方案对已提交事实的含义.
