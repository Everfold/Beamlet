# 持久化与恢复

状态: 2026-11-10 确认的目标保证与实现前置约束. 当前运行时仍是易失原型, `beamlet-durable` 仍为脚手架. 本文不宣称已有跨重启恢复, 自动迁移或外部影响恰好一次保证.

## 存储范围与所有权

官方首先实现 Diesel + SQLite. 用户可以提供满足相同契约的存储后端, 当前不讨论或实现其他方案. 数据不要求 Event Sourcing; 可以使用当前状态, 不可变执行事实和必要的历史关系. 不将所有内部变化扩展为事件原语.

| 所有者 | 必须保留的数据 |
| --- | --- |
| Agent | 配置版本引用, 输入及消费位置, 有序执行引用, 选定结果, 已发布回答及其稳定位置, 所属 Loop 引用/进度, 待提交决定 |
| Authority | SubmissionKey 去重映射, Operation 定义, Attempt 授权与目标绑定, 待交付授权, 全部合法 Report |
| Worker | 已接纳 Attempt, 可能开始执行的记录, 完成 Report, 待交付责任及去重记录 |
| 组合执行宿主 | 父执行与子调用位置/SubmissionKey 的映射, 所使用证据及返回结果; Agent Loop 数据可与 Agent 合并保存 |
| 配置/内容存储 | 稳定角色身份, 不可变 preset/capability 版本, 必要请求内容与大结果内容 |

这是一张数据职责表, 不要求五个数据库或五组公共实体. Agent 数据不存入 Operation 请求以模拟可变会话, 执行账本也不依赖 Agent 当前状态才能解释旧 Report.

Agent 和执行账本可以共用一个 SQLite, 也可以分别部署. 各自拥有本地原子提交, 跨所有者通过稳定身份, 可重发消息和对账衔接, 不要求分布式事务. 远程存储服务必须原子处理一条提交请求, 并能通过稳定提交标识解决响应丢失; 不能把一组客户端消息当成已完成的数据库事务.

首版 SQL schema, 连接/迁移管理和大内容存储布局待实现时定案. 表必须能表达唯一身份, 相同身份内容冲突和一致更新, 不能仅靠程序启动时扫描内存保证去重.

## 提交顺序与异步执行

| 本地事务保存什么 | 提交成功后允许什么 |
| --- | --- |
| Agent 的输入/Report 消费位置 + 新进度 + 全部派生调用定义和 SubmissionKey | 发送这些调用 |
| Agent 的回答发布记录及其来源/内容引用 + 对应消费进度 | 通知 UI, 允许查询已保存回答 |
| Authority 的提交键映射 + Operation + 授权 + 待派发责任 | 确认持久接纳, 异步派发 Attempt |
| Worker 的 Attempt 接纳与去重记录 | 确认持久接纳 |
| Worker 已进入可能执行的阶段 | 开始外部执行; 此标记不证明实际执行已发生 |
| Worker 的最终 Report + 待交付责任 | 发送 Report |
| Authority 的完整 Report 与结果观察 | 确认已持久保留, 向 Client 提供结果 |

Agent 的多项派生请求需要一次一致保存; 不能只记录已消费结果却遗漏其派生动作. 工具结果被采用时保存后续 LLM 的处理责任, 结果收录与提交下一次 LLM 之间不能被误判为 Loop 完成. 同一结果产生的回答发布记录与消费进度也保持一致. 当前阶段下次重入读取原请求和发布记录, 不重新解释同一 Report 并生成新键.

持久化可以异步进行, 多个独立请求可以并发处理. 仅依赖提交成功的后续动作等待提交结果, 不阻塞整个 Authority, Node 或运行时线程. SQL 不包住网络等待或外部执行.

Diesel 同步 SQLite 操作由数据库线程或阻塞任务承载, 上层异步接收提交结果. SQLite 单个数据库同一时间只有一个写事务; 可使用有界写队列和短事务, 将多个独立请求批量提交后分别唤醒. 批量失败不能给其中未提交请求发肯定回执, 批量等待也不得无限延长. 队列上限属于存储 Adapter, 不是 Operation 全局调度名额.

需在上线前声明故障范围: 进程崩溃与系统掉电的保证不同. SQLite 日志模式, 同步设置, 文件系统与备份策略必须匹配声明, 不将所有配置统称为完全耐久. 外部数据源不可达时保留未确认, 不静默切换到空内存账本继续执行.

## 故障窗口与恢复动作

下表以持久提交已兑现且原执行权可安全恢复为前提. 新实例获得执行权还有下一节的限制.

| 崩溃或失联位置 | 已保留事实 | 恢复动作与禁止事项 |
| --- | --- | --- |
| Agent 决策事务提交前 | 旧消费位置, 无新调用承诺 | 可重新处理未消费输入; 此前不得已发送这些新调用 |
| Agent 已保存调用, 尚无接纳映射 | 原请求, 目标 Authority, SubmissionKey | 查询或重传原提交; 不换键, 不猜测未接纳 |
| Authority 已接纳, 回执丢失 | 原键到 Operation/Attempt 映射 | 重复提交返回原映射; 不生成另一执行 |
| Authority 已接纳, Worker 接纳未确认 | 原授权与投递责任 | 在合法实例/恢复绑定下重传原授权; 不因超时改派 |
| Worker 已接纳, 可证明尚未进入执行阶段 | 原授权与排队记录 | 在执行权重新确认后恢复原排队责任 |
| Worker 已标记可能执行, 尚无最终 Report | 原授权, 可能已发生外部影响 | 保留未知, 对账或使用 capability 明确支持的恢复; 不直接重跑 |
| Worker 已保存 Report, 交付未确认 | 原 ReportId, 内容与待交付责任 | 重传原 Report, 不重新执行工具 |
| Authority 已保留 Report, 回执/通知丢失 | 完整证据 | 对重复 Report 再确认; Client 查询补齐 |
| Agent 已看到 Report, 尚未保存采用决定 | Authority 有 Report, Agent 消费位置未推进 | 重新获取并处理; 不执行未提交的派生动作 |
| Agent 已保存采用决定与后续调用 | 原消费位置及派生映射 | 继续既有决定, 不分配另一组子调用 |
| Agent 已保存回答, UI 通知丢失 | 原回答记录, 稳定位置及来源/内容引用 | UI 查询补齐, 重复通知按位置去重; 不重新调用 LLM 或生成第二条回答 |
| Loop 最终结果已保存, 外层 Report 交付未确认 | 最终结果及与 Loop Attempt 关联的完成责任 | 幂等交给 Worker/Authority; 不重新运行 Loop 或重复发布用户结果 |
| Codemode 运行中丢失执行现场 | 代码, 已提交子调用与已有证据 | 标记中断/未确认并保留子执行; 不自动从头重放代码 |

若 Agent 存储与 Worker 的 Report 存储分离, 最终结果写入 Agent 侧与 Worker 侧之间也是故障窗口. 必须保存可幂等重交的完成记录, 或使用同一数据库事务覆盖两个写入. 在该责任建立前不能丢弃活动 Loop. 无需引入两阶段提交.

数据库调用返回错误/超时可能意味着提交结果未知. 通过原提交标识或版本查询, 不直接生成新的业务动作. 只有确认事务未提交时才能按旧状态重试计算.

重复消息允许再次确认原事实. 重投次数, 退避与操作期限属于具体交付实现; 持久化重启不能清空已有预算后无限重试. 超出预算保持未确认, 后续显式恢复/对账必须沿用原身份. 当前原型的 3 次/固定秒数不是未来存储契约的常数, 也不因本设计自动修改.

## 稳定身份与实例更替

稳定 NodeId, AuthorityId, WorkerId 与每次启动的 InstanceId 分离. 原 Attempt 和 Report 的历史实例绑定不可变. 新进程加载同一稳定身份和账本, 不意味着可将原记录的实例 ID 批量替换为新实例.

恢复需要分别回答:

1. 新实例是否有权访问原账本并作为该逻辑角色运行.
2. 旧实例是否已停止或已被有效隔离, 包括不能继续发起执行和推进 Agent.
3. 哪些旧授权/交付责任可恢复, 哪些只能查询和接收迟到证据.
4. 新传输信封如何携带旧证据, 回执如何绑定当前交付与原始执行, 不改写历史身份.

第一版不根据心跳超时, 租约计时或 UUID 相同自动接管. 实例更替后的授权恢复/旧实例隔离协议是实现重启恢复前的必决项, 未完成时只能恢复查询与审阅, 不能宣称恢复了执行权. 不引入共识或跨节点自动迁移作为当前前提.

首次实现的恢复范围已确定为查询, 原消息交付和可证明安全的 Agent Loop 续行. 续行先补齐已保存的决定和执行事实, 必须确认旧推进者不能继续运行且当前授权有效. 不重跑结果未知的普通工具, 不自动恢复 Codemode 的代码执行现场. 这是能力范围, 不是当前代码已经满足安全续行条件的声明.

普通工具进入可能执行阶段后默认不重跑. 如果 capability 有外部幂等键, 查询或明确恢复协议, 只能按该固定版本契约使用, 不能从名称或成功率猜测安全性. Agent Loop 的显式状态续行与 Codemode 的整段代码重跑也不能混用.

## Agent 创建关联与停止

每个新的 Agent 创建或 fork 对应新的 Agent 与 Loop Operation. 保存 Operation 与 Agent 的创建关联, 重复初始化或恢复时加载原有数据; 相同配置的不同创建请求保持独立. 无需额外预留已有 Agent 的活动 Loop, 也不提供由两个独立 Operation 共同推进同一 Agent 的入口.

同一 Attempt 的重复交付与执行恢复遵守通用 Worker 契约. 重启后是否可以继续原执行由上一节的实例更替规则决定, 不另外建立 Agent 专用锁或执行权协议. 原执行内部对输入, Report 消费位置和派生动作保持一致更新.

停止发起新调用, 取消等待, 请求工具取消, 已证实停止, 交付完成和正常完成分别记录. Node Draining 处理进程退出, 不替代 Agent 的业务停止契约. 永久服务由外部管理器负责; 工具已成功启动服务后不把其持续存活当作待回收工具.

## 引用保留, 版本与清理

Agent 与 fork 副本引用的 Operation, Attempt, Report, preset/capability 版本及请求内容必须可查询. 删除原 Agent 不自动删除共享执行事实. 不能只保留 provider 格式化后的 prompt 而丢弃被采用的原证据.

首版采用保守保留: 不自动删除仍被引用的记录, 不以终态为由删除去重映射后再次接纳同键. 未实现跨存储引用登记时, 不启用会破坏引用的自动清理. 后续若引入期限, 墓碑或归档, 必须明确过期查询与重提交行为, 不能把过期当作从未存在.

Schema 与序列化记录需要版本和明确迁移路径. 老记录无法解释时停止相关执行并报告, 不按新默认值重建未知事实. preset/capability 固定版本, provider 请求保留实际输入, 查询缓存不能覆盖这些权威记录.

## 权限与证据范围

AgentId, AuthorityId, parent AttemptId 和来源关联均不授予权限. 首版采用静态可信配置, 明确授权可调用 capability, 参数/资源范围, 查询范围与 Agent 推进权. Codemode 工具接口遵循相同限制, 不直接获得宿主凭据或任意文件/网络能力.

Report 中影响证据只针对声明的执行范围, 不从执行成功/失败推导, 不自动聚合父子影响. 目标类型名为 `ImpactStatus`, 字段名为 `impact`; Rust 类型和原型消息字段已统一更名, 不保留旧编码兼容层; 尚未实现的持久存储直接采用新名称. 保留结果意味着收录证据, 不意味着 Authority 证明外部世界绝对正确或保证影响仅发生一次.
